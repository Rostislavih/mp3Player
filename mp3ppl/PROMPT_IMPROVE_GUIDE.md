## Что не так сейчас (с конкретными примерами)

В файлах гайда часто встречается шаблон: **«вот код, дальше шаг 9»**, без раскрытия **что делает каждая значимая строка** и **почему именно так, а не иначе**.

### Пример 1 — `02-PERMISSIONS_AND_SCAN.md`, Шаг 8 (`AlbumsRepositoryImpl`)

В коде есть выражение:

```kotlin
private fun groupIntoAlbums(tracks: List<Track>): List<Album> =
    tracks
        .groupBy { it.albumId }
        .map { (albumId, items) ->
            val artists = items.map { it.artist }.distinct()
            val artist = if (artists.size == 1) artists.first() else "Various Artists"
            Album(
                id = albumId,
                title = items.first().album,
                artist = artist,
                trackCount = items.size,
                coverUri = items.firstOrNull { it.coverUri != null }?.coverUri,
                totalDurationMs = items.sumOf { it.duration },
            )
        }
        .sortedBy { it.title.lowercase() }
```

В тексте после кода **не объяснено**:
- что именно вернёт `groupBy { it.albumId }` (тип, форма данных, пример),
- почему дальше `.map { (albumId, items) -> ... }` — что это за деструктуризация пары и откуда она берётся в `Map.Entry`,
- что `.map` здесь — это **`List.map` из stdlib, а не `Flow.map`** (хотя выше в этом же файле использовался `Flow.map`); чем они отличаются, и почему здесь синхронно,
- зачем `items.map { it.artist }.distinct()` и почему `if (artists.size == 1)` решает проблему «Various Artists»,
- почему `items.first().album` безопасно (откуда гарантия, что список не пустой),
- зачем `firstOrNull { it.coverUri != null }?.coverUri` вместо `items.first().coverUri`,
- что делает `sumOf { it.duration }`,
- зачем `.sortedBy { it.title.lowercase() }` и **почему именно `lowercase()`** (что без него `"яблоко"` улетит после `"Я"` или `"a"` после `"Z"` из-за порядка кодпойнтов; это и есть «суть»).

После доработки **каждый из этих пунктов** должен быть разобран — не общими словами, а с привязкой к конкретной строке.

### Пример 2 — Шаг 7 (`TracksRepositoryImpl`)

```kotlin
private val _tracks = MutableStateFlow<List<Track>>(emptyList())
private val scanLock = Mutex()

override fun observeTracks(): Flow<List<Track>> = _tracks.asStateFlow()

override suspend fun refresh() {
    scanLock.withLock {
        _tracks.value = scanner.scanTracks()
    }
}
```

Сейчас сверху есть пара абзацев «Почему `Mutex`» и «Почему `StateFlow`», но **студент всё равно не понимает**:
- что `Mutex` — это **корутинный** примитив, а `synchronized` — **поточный**, и почему это важно (не блокирует поток, освобождает его пока корутина «спит»);
- что `withLock { ... }` — это `lock()` + `try/finally + unlock()`, а не магия;
- что `MutableStateFlow` хранит **одно** значение и `=` присваивание `.value` атомарно публикует новое значение всем подписчикам;
- зачем `_tracks` приватный, а наружу отдаётся `asStateFlow()` — что именно мы прячем (mutability), и почему read-only-обёртка важна для архитектуры;
- что значит «корутина приостанавливается» (suspend point), и почему `scanner.scanTracks()` внутри `withLock` безопасно — лок отдаётся даже при отмене корутины.

### Пример 3 — `06-VIEWMODELS_AND_STATE.md`, конструкция `stateIn`

```kotlin
.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5_000),
    initialValue = TracksUiState(isLoading = true),
)
```

Сейчас разбор есть, но поверхностный. Нужно добавить:
- **что физически делает `stateIn`**: превращает «холодный» `Flow` в «горячий» `StateFlow`, запускает upstream-корутину в указанном `scope`,
- **что такое холодный vs горячий поток** на бытовом примере (холодный = плёнка в кассете, горячий = радиоэфир),
- **что такое `SharingStarted.WhileSubscribed(5000)`**: подписка на upstream живёт пока есть хоть один collector, плюс 5 секунд после ухода последнего; зачем эти 5 секунд (поворот экрана не должен ронять подписку);
- **что такое `viewModelScope`**: scope, который автоматически отменяется в `onCleared()` — память не течёт, корутины умирают вместе с ViewModel.

## Концепции, которые точно требуют глубокого разбора

В каком-то месте гайда (там, где они впервые появляются) каждый из этих терминов должен быть разобран **до сути**. Если уже есть мини-разбор — углуби. Не дублируй между файлами: сошлись на первое появление.

| Термин | Что обязательно объяснить |
|---|---|
| `suspend` | Что компилятор добавляет неявный параметр `Continuation`; что вызов `suspend`-функции — это **не блок потока**, а пометка точки, в которой корутина может «уснуть» и потом продолжить. |
| Корутина | Что это «кооперативная задача», которая отдаёт поток обратно в пул на suspend-точке. Чем отличается от потока (тысячи корутин на одном потоке — норма). |
| `Dispatchers.IO` / `Default` / `Main` | Какой пул для каких задач, что бывает при путанице (фриз UI), что `withContext(IO)` переключает контекст **внутри** suspend-функции и сам же возвращает обратно. |
| `withContext(...)` | Что это suspend-функция, которая **дожидается** результата блока; в чём разница с `launch` (`launch` запускает «в сторону» и возвращает `Job`). |
| `Flow` (cold) | Что код внутри `flow { ... }` / `.map { ... }` выполняется **на каждого подписчика заново**; что без `collect` ничего не происходит. |
| `StateFlow` (hot) | Что это `Flow`, который всегда имеет текущее значение и пере-эмитит его новому подписчику. Зачем так для UI. |
| `MutableStateFlow.value =` | Что присваивание атомарное, что подписчики получают только различающиеся значения (`distinctUntilChanged` встроено), что значит «conflated». |
| `asStateFlow()` | Что это апкаст: тот же объект, но без `setter` снаружи. Зачем (инкапсуляция). |
| `Flow.map` vs `List.map` | Что это **разные функции с разной семантикой**: `Flow.map` — оператор потока (трансформация на каждый emit), `List.map` — синхронный обход коллекции. Имя одинаковое — это совпадение API. |
| `Mutex` / `withLock` | Корутинный лок: блокирует **корутину**, не поток. Что не реентрант (если повторно войти из той же корутины — дедлок). Когда лучше брать `Mutex`, а когда — `Channel` или `actor`-паттерн. |
| `viewModelScope` | Откуда берётся (artifact `lifecycle-viewmodel-ktx`), что отменяется в `onCleared()`. |
| `stateIn` / `SharingStarted` | Холодное → горячее. `Eagerly` / `Lazily` / `WhileSubscribed(timeout)` — когда что выбирать. Почему 5 секунд — стандарт. |
| `collectAsStateWithLifecycle` | Чем отличается от `collectAsState`: учитывает lifecycle, не собирает поток когда экран в фоне. |
| `LaunchedEffect(key)` | Когда перезапускается, чем отличается от `SideEffect`, `DisposableEffect`. |
| `remember { }` / `mutableStateOf` | Что `remember` хранит между рекомпозициями, `mutableStateOf` — состояние, на которое подписывается Compose. |
| `expect` / `actual` | Что это статическая «мульти-реализация», разрешается компилятором по target'у; не путать с интерфейсом (нет vtable). |
| `groupBy` / `map { (k, v) -> }` / `sortedBy` / `sumOf` / `firstOrNull` / `distinct` | Каждая в одном-двух предложениях с примером **на конкретных треках** из текущего шага. |
| `?.use { }` | Что `Closeable.use` — это аналог try-with-resources; что курсор без `use` течёт. |
| `Build.VERSION.SDK_INT >= ...` | Зачем рантайм-проверка, что API-уровень = версия Android, что бывает при отсутствии (`NoSuchMethodError` на старых устройствах). |
| Room: `@Entity`, `@Dao`, `Flow<List<X>>`, `@Relation`, `@Transaction` | Что Room — кодоген, что `Flow` из DAO эмитит при изменении таблицы; зачем `@Transaction` для `@Relation`. |
| Media3: `MediaSession`, `MediaSessionService`, `Player.Listener` | Что сервис нужен для жизни плеера в фоне, что MediaSession даёт системе ручки управления (lockscreen, BT). |

## Принципы пояснений

1. **Привязка к строке.** Любое объяснение должно начинаться со ссылки на конкретную строку или фрагмент: «На строке 326 `.map { tracks -> groupIntoAlbums(tracks) }` — это `Flow.map`…». Никаких «вообще говоря, в Kotlin есть…».
2. **Доходи до сути, без отговорок.** Запрещены формулировки типа «это просто работает», «магия Kotlin», «считай это чёрным ящиком». Если объясняешь `suspend` — упомяни `Continuation`. Если `Mutex` — скажи, что это очередь корутин.
3. **Не абстрагируйся.** Не давай определений «вообще», давай определения **на этом коде**: «`groupBy { it.albumId }` здесь возьмёт список треков и вернёт `Map<String, List<Track>>`, где ключ — `albumId` (вроде `"4711"`), а значение — все треки этого альбома».
4. **«Что было бы без этой строки» — мощный приём.** «Если убрать `.lowercase()`, `"Apple"` окажется выше `"banana"` из-за `A` < `b` в Unicode, но `"Яблоко"` улетит в самый конец». Используй такой формат регулярно.
5. **Сравнивай похожее.** `Flow.map` vs `List.map`. `withContext` vs `launch`. `StateFlow` vs `SharedFlow`. `Mutex` vs `synchronized`. `LaunchedEffect` vs `SideEffect`. Сравнения помогают не путаться.
6. **Не бойся длины, но не лей воду.** Если разбор честно требует 30 строк — пиши 30. Но не растягивай ради объёма.
7. **Один термин — один источник правды.** Если `Flow` подробно разобран в файле 02 — в файле 06 просто сошлись: «Подробно `Flow` разбирали в [`02-PERMISSIONS_AND_SCAN.md` → раздел «Холодный поток»]». Не дублируй.
8. **Сохраняй уже хорошее.** Текущий гайд **не переписывать целиком**. Дополнения встраивай, а сжатые места, где всё и так ясно, — не трогай.
9. **Русский язык.** Технические термины оставляй латиницей (`Flow`, `Mutex`, `StateFlow`), окружающий текст — по-русски. Стиль — на «ты», как в существующем гайде.

## Формат вставки пояснений

Внутри каждого шага используй **два уровня**:

### A. Inline-комментарии в самом коде
Только там, где иначе строка нечитаема. Минимум, но по делу:

```kotlin
.map { (albumId, items) ->                        // деструктуризация Map.Entry: ключ + значение
    val artists = items.map { it.artist }         // List.map: вытащить имя исполнителя из каждого трека
        .distinct()                               // оставить уникальные → если 1 → общий артист
```

### B. Раздел «Разбор по строкам» **сразу после** блока кода
Подзаголовки = конкретная строка / выражение:

```markdown
#### `groupBy { it.albumId }`

Вернёт `Map<String, List<Track>>`. Ключ — строковый `albumId` (тот, что мы получили из MediaStore.ALBUM_ID и сохранили в Track). Значение — список всех треков, у которых этот `albumId` совпадает.

Пример: если в библиотеке три трека с `albumId = "42"` (Dark Side of the Moon) и два с `albumId = "7"` (Wish You Were Here), результат:
```
"42" -> [Track("Money", ...), Track("Time", ...), Track("Brain Damage", ...)]
"7"  -> [Track("Wish You Were Here", ...), Track("Have a Cigar", ...)]
```

#### `.map { (albumId, items) -> ... }`

Это `Map.map { entry -> ... }` из stdlib. **Не `Flow.map`** — мы уже работаем с обычной коллекцией. ...
```

Существующий раздел `## Разбор` в конце файла можно **оставить для общих концепций** (Dispatchers, Mutex), а пошаговые `#### `строки`` — встраивать сразу после соответствующего шага. Решай по месту.
